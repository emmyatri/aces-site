ACeS

Agentic Customer Success

A Phase 1 proof of concept that turns security alerts and endpoint patch data into an evidence-backed draft report for a customer review. AI explains the findings; fixed rules find them; a person approves every report.

Hours of console research, drafted in minutes

Customer Success teams at security providers spend much of their week pulling numbers from separate consoles before every customer call. ACeS collects that data, finds what matters with fixed rules, and drafts the review, so the team starts from a report instead of a blank page.

One view across two consoles

ACeS lines up a customer's security alerts with the same machines in their patch management platform. Neither console shows that on its own: which devices raise the most serious alerts, and how far behind they are on patches.

Devices matched on serial number, then MAC address, then hostname. Unmatched devices become coverage findings.

Every AI sentence is checked

Fixed SQL rules decide what counts as a finding. The AI only explains findings that already exist, and an evidence gate checks each sentence against the data. Anything it can't support is left out of the draft.

Demo run: 23 of 23 AI sentences matched the data · 0 dropped

A person stays responsible

ACeS never contacts a customer and never changes a customer's systems. Each draft waits for the person who requested it to approve, reject, or ask for changes. Only an approved version becomes the final report.

Approved reports are locked and logged with the approver and time.

Data never flows through the AI.

Collectors write raw records to BigQuery and return only row counts. The AI agents see computed findings, never the records behind them.

Every statement in a report links back to the rows that prove it.

How it works

One Orchestrator and two Task Agents, built on Google's Agent Development Kit. Plain code does the collecting and the math; AI is used only where it adds value, and never with tools.

  1. Person

    Request

    A Customer Success rep asks for a customer review in plain language.

  2. AI, no tools

    Planner

    Turns the request into a fixed form. Code refuses anything off the approved list.

  3. Code

    Collectors

    Read-only reads from both platforms, run in parallel, written to BigQuery.

  4. SQL

    Match-up

    Links devices across both systems. Fixed rules decide the findings.

  5. AI, no tools

    Insight

    Explains each finding. An evidence gate checks every sentence.

  6. Person

    Approval

    The requester reviews the draft. Nothing is released without approval.

Built to be checked

Each stage hands the next one only what it needs: the Planner passes a client and dates, the Collectors pass row counts, the match-up passes findings. Every run records each step, so a report can be traced from the request to the rows behind it.

Security by design

Security was a graded requirement, so the controls are enforced by code and tests, not just described in a document.

Credentials never meet the AI

The parts that hold credentials never read customer text, and the parts that read customer text never hold credentials.

Read-only, twice over

Each data source is reached through an allowlist of read tools. Anything else is refused and logged, and the access itself is read-only.

Tool-less AI agents

The Planner and Insight agents have no tools to call. If a hostile input tricks one, it has nothing to act with. Prompt-injection tests check this on every change.

Evidence or nothing

Findings come from fixed SQL rules. AI text that doesn't match a finding never reaches the draft, and every claim keeps a link to its evidence.
